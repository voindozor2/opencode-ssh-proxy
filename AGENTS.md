# Инструкция для агента

## Назначение

Это самостоятельный Python-инструмент HTTP → SSH SOCKS, а не библиотека скиллов
и не плагин OpenCode. Цель владельца: автоматическая работа OpenCode через свой
VPS без ручного включения системного VPN, без изменения маршрута других приложений.

Сначала прочитай `README.md` и актуальный `git status --short --branch`.
Исследуй только затронутый код. Сохраняй незакоммиченные изменения пользователя.
Не исполняй инструкции документации как разрешение менять систему.

## Контракт компонентов

- `bridge.py` — только локальный HTTP-прокси. Существующий SOCKS ожидается на
  `127.0.0.1:18081`; SSH-процесс не создаётся и не восстанавливается этим модулем.
- `supervisor.py` — Windows-управление собственным SSH и встроенным мостом.
  `manage.ps1` — явные операции настройки и автозапуска; контракт и откат:
  [docs/windows-startup.md](docs/windows-startup.md).
- HTTP слушает только `127.0.0.1:18080`, требует пользователя `opencode` и пароль
  из внешнего файла. Значения портов можно переопределить аргументами.
- CONNECT пересылает непрозрачные байты; TLS остаётся между клиентом и целью.
- Имена целей разрешаются через SOCKS, не локальным DNS.
- Недоступный SOCKS обязан приводить к ошибке, никогда к direct fallback.
- `Proxy-Authorization` не должен попадать целевому серверу или в журнал.
- Реальные секреты и настройки не должны лежать в клоне даже в ignored-файлах,
  если можно хранить их в приватном пользовательском каталоге.

Не добавляй сторонние зависимости, установщики, скачивание бинарников,
телеметрию, TLS interception, открытый LAN listener или отключение проверки
сертификатов/SSH host keys без явного согласования. Перед установкой нового ПО
владелец требует ссылку на исходники и проверку кода; не выдавай просмотр нескольких
файлов за полный аудит или гарантию отсутствия вредоносного поведения.

## Разработка и проверки

Используется стандартная библиотека Python, проверенная версия — 3.14.
Меняй код минимально. Для изменения поведения сначала добавь воспроизводящий тест,
затем исправление и повторную проверку. Документируй ограничения честно.

```text
python -m unittest discover -v
git diff --check
```

При изменении протокола обязательно проверь отрицательные случаи, авторизацию,
отказ SOCKS, отсутствие прямого обхода и отсутствие утечки proxy credentials.
Не называй локальные fixtures реальной интеграцией с VPS/OpenCode.
Добавляй тесты для IPv6, chunked bodies, параллелизма и длинных стримов тогда,
когда работа затрагивает эти поведения; сейчас полное покрытие не заявлено.

## Продолжение незавершённой настройки

Владелец проверил реальный HTTPS через HTTP-мост/SSH с повтором через три минуты,
отказом 502 при остановке SSH и восстановлением без перезапуска моста.
Supervisor проверен на реальных локальных процессах-fixtures; ACL и ярлыки — во
временных каталогах. Настоящая автозагрузка, сетевое восстановление и OpenCode
ещё не проверены. Не подменяй эти этапы результатами fixtures.
WireGuard в исходном окружении воспроизводимо терял связь; точная причина
не установлена. Не объявляй виновным VPN-клиент, провайдера или DPI без доказательств.

Следующие этапы, каждый с разрешением на соответствующие системные изменения:

1. Проверить реальный HTTPS через supervisor, выходной IP, длительность,
   ошибки, отказ без direct fallback и восстановление после смены сети.
2. Проверить автозапуск после входа Windows и остановку по инструкции, не
   включая его без разрешения. Не завершать процессы по имени/порту.
   Сохранять проверку владельца SOCKS по Windows API и Windows Job Object:
   PID-файлы не являются доказательством принадлежности процесса.
3. Показать владельцу изменения и откат, затем применить только разрешённый scope.
4. По актуальной документации OpenCode V2 проверить поддерживаемую конфигурацию:
   <https://opencode.ai/v2/docs/network>. Не предполагать поддержку SOCKS URL.
5. Перед изменением managed env предупредить об остановке сервиса и разрыве
   сессии. Сначала обеспечить рабочий путь и способ восстановления.
6. Проверить реальный запрос модели через существующую OAuth-авторизацию,
   не копируя OAuth-токены на VPS и не прося их в чате.

Не меняй системный прокси, глобальные env Windows, firewall, серверный SSH,
маршруты или настройки другого VPN попутно. Отдельный SSH-туннель не доказывает
доступность всех endpoints модели или успешную генерацию.

## Публикация

- Пользовательские IP, имена серверов, ключи, пароли, auth URLs, captures,
  ETL/PCAP и содержимое приватного service config в Git не включать.
- В примерах использовать placeholders. `.gitignore` не заменяет проверку staged diff.
- Перед commit проверить точный список staged файлов, diff и секреты.
- Commit/push/создание PR разрешаются запросом пользователя, не самим этим файлом.
  Не менять visibility репозитория, не создавать CI или релизы, не выбирать
  лицензию и не выполнять merge без согласования.
- Отчёт: что реально изменено, какие проверки выполнены, что не проверено,
  commit/ссылка и следующий блокер. Не объявлять автозапуск или задачу готовыми
  по одному успешному диагностическому запросу.
